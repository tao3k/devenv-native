This file is an architecture blueprint template.

A blueprint captures the durable architectural design for a workstream: the
target shape, governing boundaries, invariants, and approved direction for the
next 1-3 slices.

A blueprint is not an ExecPlan, not a task checklist, and not a change log. If
a detail is slice-local, command-oriented, or validation-log oriented, it
belongs in an ExecPlan under =$PRJ_CACHE_HOME/agent/execplans/=.

** Architectural Objective

Describe the architectural problem this blueprint governs and the durable
outcome it is meant to secure.

Record:

1. why this workstream exists
2. what architectural condition must become true
3. why this belongs in a blueprint instead of only in an ExecPlan

** System Context and Design Drivers

*** Current Reality

Describe the current architecture, pain points, or constraints that make this
blueprint necessary.

*** Design Drivers

List the forces that should shape the design. Examples:

1. correctness or safety constraints
2. package ownership boundaries
3. protocol or interface stability
4. runtime or operational requirements
5. migration pressure from older surfaces

** Target Architecture

*** Target Shape

Describe the intended architectural shape in durable terms.

*** Responsibilities and Ownership

State which package, subsystem, or layer owns each major responsibility.

*** Interfaces and Data Contracts

Record the stable interfaces, data boundaries, or protocol contracts this
blueprint expects.

*** Failure Model and Operational Expectations

State the expected failure handling, fallback model, observability, or runtime
behavior that must remain coherent with the architecture.

** Design Principles and Invariants

List the non-negotiable architectural rules that every ExecPlan under this
blueprint must preserve.

*** Principle / Invariant

State one durable rule and explain why it must remain true.

** Governed Boundaries

List what this blueprint explicitly governs.

*** Ownership Boundaries

State which team, crate, package, or layer owns which concern.

*** Protocol Boundaries

State which interfaces, schemas, or transport surfaces are in scope.

*** Package or Subsystem Boundaries

State the concrete package, module, or service edges that must stay explicit.

*** Non-Goals

List what this blueprint does not attempt to solve so later ExecPlans do not
silently widen scope.

** Key Decisions and Rejected Alternatives

*** Chosen Direction

Record the primary architectural decision.

*** Rejected or Deferred Alternatives

Record the main alternatives considered and why they were rejected or deferred.

*** Revisit Triggers

State the conditions that would justify revisiting the design.

** Immediate Evolution Slices

Define the next 1-3 slices this blueprint authorizes.

For each slice, record:

1. architectural purpose
2. prerequisite dependencies or proofs
3. expected completion signal

Do not turn this section into a step-by-step execution script.

** Risks, Unknowns, and Required Evidence

*** Risks and Unknowns

List the architectural risks, open questions, or assumptions that still need
proof.

*** Required Evidence

Record the evidence needed before the architecture can be considered stable.

Examples:

1. contract tests
2. migration proofs
3. load or latency measurements
4. failure-mode validation
5. package-doc updates

** Alignment Audit Rules

Record the conditions that must remain true when an ExecPlan or implementation
claims alignment to this blueprint.

Minimum checks:

1. target architecture remains the guiding shape
2. invariants are preserved
3. governed boundaries stay explicit
4. no hidden coupling or scope drift is introduced
5. slice-level execution details stay in the ExecPlan, not in the blueprint
