# Pragmatic Ontology Extensibility and SQL-Driven Validation

## 1. Vision and Motivation

While W3C standards (RDF/OWL) provide a robust foundation for semantic modeling, standard semantic validation languages (like SHACL or SPARQL) present a steep learning curve for human operators and are notoriously prone to syntax hallucinations when generated by Large Language Models (LLMs).

This RFC outlines a pragmatic approach for the `xiuxian-artisan-workshop` architecture:

1. **Reviewable Expansion**: Using Org ledgers for human, agent, and LLM
   ontology proposals because Org can carry state, property drawers, dates,
   evidence, source spans, and appendable reasoning in one parseable format.
2. **Stable Semantic Authority**: Using RDF or RDF-shaped proposal artifacts
   for accepted ontology meaning after validation.
3. **Domain-Encapsulated Validation**: Using SQL through DuckDB/DataFusion over
   Arrow/Parquet read models as the primary engine for ontology constraint
   validation, co-located within specific domain directories.

## 2. Authoring and Extension Interfaces

Org is the preferred proposal and reasoning interface. It is the durable ledger
for mapping intent, candidate lifecycle state, evidence anchors, review
decisions, and agent/LLM additions. TOML remains useful for compact extension
configuration and bootstrap metadata, but it should not replace Org as the
reviewable ontology reasoning surface.

Users or external systems can extend the L1 Domain ontology simply by placing an `ontology.toml` file in their configuration directory.

```toml
[ontology.metadata]
extends = "episteme://10_Software_Engineering"
namespace = "local_project"

[[entity]]
id = "CustomDeploymentPipeline"
base = "Deployment"
description = "Internal specific deployment routine for Alpha client"

[[relation]]
source = "Engineer"
target = "CustomDeploymentPipeline"
type = "authorizes"
```

The Rust orchestrator compiles reviewed Org/TOML inputs into internal semantic
triples, resolving inheritance and shadowing upstream defaults. Accepted
semantic outputs are materialized as RDF or RDF-shaped proposal artifacts, then
compiled into Arrow/Parquet read-model tables for runtime validation and search.

## 3. Domain-Encapsulated SQL Validation

Validation logic (SQL) and behavioral policies are strictly domain-specific. A monolithic rule repository violates high cohesion. Therefore, physical directory structures must encapsulate constraints alongside their respective vertical domain definitions within `wendao-episteme/ontology/`.

### Directory Convention

Each vertical domain within the L1 tier operates as a self-contained module:

```text
wendao-episteme/ontology/10-49_L1_Domain/
└── 10_Software_Engineering/
    ├── ontology.rdf            # Structural definitions (Classes & Properties)
    ├── policies/               # Domain-specific Agent guidelines (Markdown)
    │   └── architectural_decision_making.md
    └── rules/                  # Domain-specific SQL constraints (DuckDB)
        ├── 01_rfc_must_have_author.sql
        └── 02_implementation_must_link_rfc.sql
```

### The "Plug-and-Play" Validation Pipeline

When a user extends an ontology (e.g., `extends = "episteme://10_Software_Engineering"`), the system mounts **only** the SQL rules located within that specific domain's `rules/` subdirectory. This ensures that validation is strictly sandboxed to the active business context.

Validation queries run against typed Arrow/Parquet read models compiled from
reviewed Org/RDF/structural-fact inputs. TSV files are not canonical validation
inputs for new ontology flows; they may exist only as legacy compatibility
projections while callers migrate to columnar read models.

## 4. The Agentic Self-Healing Loop

If a DuckDB validation query fails (returns violating rows), the exact SQL query and the violator rows are passed back to the Sub-agent. Because LLMs possess native fluency in SQL, the Sub-agent instantly understands the relational failure and autonomously patches the user's TOML file, closing the self-healing loop without requiring knowledge of esoteric semantic web languages.

## 5. Academic References & Extensions

The methodologies in this RFC are supported by the most recent advancements (2025-2026) in Neuro-Symbolic RAG and Agentic workflows:

- **Neurosymbolic Retrievers for Retrieval-Augmented Generation (2026)**: _Saxena et al._ formalized the "Hybrid RAG" stack, proving that traversing formal knowledge graphs alongside semantic search drastically improves interpretability and reasoning quality. Our DuckDB SQL engine acts as the formal reasoning layer, grounding the LLM's output.
- **CyberCane: Neuro-Symbolic RAG with Formal Ontology Reasoning (2026)**: Demonstrated a dual-phase pipeline where deterministic symbolic rules (Phase 1) filter constraints before neural generation (Phase 2). This exactly mirrors our architecture: SQL constraints physically block illegal ontology mutations before the Sub-agent attempts self-healing.
- **Self-Evolving Knowledge Graphs for Intelligent Agents (2025)**: Research demonstrates that agents perform best when given explicit feedback loops. Our design of returning failing DuckDB rows directly to the Sub-agent mirrors the "Critic-Revision" cycles proven to maximize agentic self-correction.
