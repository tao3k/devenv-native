# Dynamic Ontology SDK (OSDK) Generation for Agentic Autonomy

## 1. Vision and Motivation

As `xiuxian-artisan-workshop` scales, forcing AI agents (or human developers) to interact with the system via raw HTTP/REST APIs, arbitrary SQL queries, or fragile string-based graph traversals creates immense friction and hallucination risks.

Inspired by Palantir AIP's philosophy of "deprecating the backend," this RFC establishes the **Ontology SDK (OSDK) Mode**. The core principle is that the Ontology is the sole API of the organization. Instead of writing backend routes to expose data, the system automatically generates a type-safe, native SDK (e.g., in Python) directly from the `wendao-episteme` semantic definitions.

This OSDK becomes the exclusive, bulletproof interface through which Sub-agents read the state of the world and propose actions.

## 2. The OSDK Generation Pipeline

The generation of the OSDK is a deterministic compilation step managed by the Rust orchestrator.

### 2.1 The Source of Truth

The Rust compiler (`xiuxian-wendao-server`) monitors the `wendao-episteme/ontology/` directory (including Foundation, Domain, and local TOML overrides). This RDF/TOML structure defines all valid `Entities`, `Relations`, and `Actions`.

### 2.2 Dynamic Code Emission

Upon detecting ontology changes, Rust executes a code-generation pass. It emits a native Python package (e.g., `wendao_osdk`) utilizing modern typing (Pydantic/Dataclasses).

For example, an ontology definition of a `SoftwareComponent` that `dependsOn` a `Database` translates into strict Python classes:

## 3. The Agentic Impact: Semantic Over Syntax

By forcing Sub-agents to use the OSDK, we fundamentally shift how LLMs interact with the codebase.

### 3.1 Hallucination-Free Querying

Instead of an Agent generating a hallucinated SQL query (`SELECT * FROM components WHERE type='db'`), which might fail or violate schema, the Agent writes native Python using the OSDK.
The LLM's autocomplete and static analysis tools instantly guide it to correct usage. If an entity doesn't exist in the OSDK, the Agent knows it cannot be queried.

### 3.2 Action-Oriented Proposals (The Kinetic Layer)

Agents are stripped of direct execution privileges (e.g., they cannot directly run `git commit` or execute shell scripts). All state mutations must be routed through OSDK `Action` classes.

```python
# Agent proposes a refactor Action
from wendao_osdk.actions import ProposeRefactor

action = ProposeRefactor(
    target_component="auth_service",
    evidence_rfc="RFC-104",
    proposed_diff="... unified diff ..."
)
action.submit_for_approval() # Enters the BPMN approval queue, does not execute immediately
```

This enforces the "Automation Ladder," ensuring that agentic intent is captured structurally and routed through human-in-the-loop or deterministic CI validation gates before altering physical reality.

## 4. Architectural Advantages

1. **Type Safety at the Edge**: The LLM operates entirely within a strongly-typed sandbox. Type errors in the agent's reasoning are caught locally by Python before ever hitting the Rust backend.
2. **Abstracted Complexity**: The OSDK completely hides the underlying complexity of DuckDB, Arrow Flight, and RDF Triples. The Agent only sees business logic.
3. **Implicit Authorization**: The OSDK client is initialized with the Agent's identity payload. The generated methods implicitly append this identity to all underlying Arrow Flight requests, allowing DuckDB SQL policies to enforce strict Data Governance and Role-Based Access Control (RBAC) at the row level.

## 5. Conclusion

The OSDK acts as the ultimate translation layer between the rigorous mathematical backend (Rust/Julia/Arrow) and the probabilistic reasoning engine (LLM Agents). By auto-generating a native, type-safe API from the Ontology, we guarantee that AI agents operate safely, predictably, and entirely within the defined physical and business laws of the enterprise.
