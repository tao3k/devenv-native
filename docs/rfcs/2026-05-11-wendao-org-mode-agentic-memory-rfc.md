# Org-Native Ontology Authoring and Trace Projection

## 1. Summary

This RFC calibrates the Org-mode memory direction into an ontology authoring
and trace-projection contract.

Org-mode is the preferred authoring syntax for human and agent-authored
ontology proposals because it can express hierarchy, metadata, lifecycle state,
tables, evidence, and embedded validation notes in one auditable plain-text
form. It is also the preferred intermediate format for long-running agent
reasoning traces, extraction notes, strategy-flow plans, and self-correction
records.

`orgize` parses those authoring documents and traces into typed sections,
property drawers, TODO state, tags, planning metadata, and tables. That parsed
structure may be compiled into ontology source-contract rows, RDF/TOML/API
surface outputs, registry snapshots, or candidate semantic rows for validation.

Org-mode has the right syntax for ontology authoring, but raw Org output does
not own ontology truth. Canonical ontology source contracts remain under
`wendao-episteme/ontology/`; Rust parser validation and repo-native semantic
governance decide whether an authored proposal becomes accepted semantic truth.

The canonical data-surface split is:

1. **Org is the durable reasoning ledger**. It is the primary working surface
   for humans, agents, and LLMs because it can carry appendable reasoning,
   headings, lifecycle state, property drawers, planning dates, source spans,
   tables, evidence notes, and review decisions in one parseable document.
2. **RDF is the semantic proposal or truth surface**. Accepted ontology meaning
   is expressed through RDF or RDF-shaped proposal artifacts after validation
   and review, not through raw model output.
3. **Arrow/Parquet is the runtime read model**. Search, proof, SQL validation,
   Julia graph computation, and Flight handoff should consume typed columnar
   read models compiled from Org, RDF, and deterministic structural facts.
4. **TSV is not a semantic contract**. Existing TSV files may remain as legacy
   compatibility projections, but new ontology semantics, provenance, or graph
   fields must target Org and Arrow/Parquet surfaces instead of widening TSV.

## 3. Motivation

Advanced Wendao workflows need an ontology authoring format and a reasoning
trace format that are both readable by humans and structured enough for
deterministic validation. Markdown is good for narrative documentation but weak
for machine-owned state, property metadata, tables, and lifecycle markers. Raw
JSON is precise but expensive for humans and fragile when long traces are
generated by an LLM. Raw RDF/XML is interoperable but poor as a primary human
or sub-agent authoring syntax.

Org-mode offers a better source-authoring and trace carrier format because it
has:

1. deterministic heading trees
2. native TODO state
3. property drawers for typed metadata
4. tags and planning metadata
5. table syntax that can be parsed without inventing an ad hoc format
6. source blocks for preserving generated RDF, TOML, SQL, or examples when
   needed
7. a human-readable review surface that still maps cleanly to parser-owned
   DTOs

The value is not that every Org document is automatically ontology truth. The
value is that ontology authors and agents can write a compact, auditable source
document that Rust can parse, validate, compile, and convert into accepted
ontology contracts or candidate evidence.

## 4. Authority Boundary

The authority split is strict:

1. `wendao-episteme/ontology/` owns source ontology contracts: Org authoring
   documents, RDF primitives, domain packs, local TOML extension contracts,
   domain SQL rule references, and SDK-facing API-surface declarations.
2. `xiuxian-wendao-parsers` owns parsing, normalization, and validation of
   Org ontology authoring documents, Org trace structures, and ontology
   source-contract files.
3. `xiuxian-wendao` consumes parser-owned contracts and exposes runtime query,
   projection, and Flight surfaces.
4. `xiuxian-wendao-sql` may execute advisory SQL validation over projected
   read-model rows.
5. Julia compute may rank, prune, or score graph projections, but its output
   remains advisory evidence.
6. LLM and sub-agent output may propose ontology candidates, but it is never
   canonical until accepted through repo-native semantic governance.
7. Generated TSV projections must never outrank Org review decisions or typed
   Arrow/Parquet read-model contracts.

## 5. Org Ontology Authoring Contract

An Org ontology authoring document should be able to express the same concepts
that a Foundry-style ontology API exposes: object types, link types, action
types, query types, interface types, value types, validation rules, provenance,
and lifecycle state.

The first parser-owned authoring contract should support this shape:

| Org unit              | Parser-owned projection                 | Ontology use                                                        |
| --------------------- | --------------------------------------- | ------------------------------------------------------------------- |
| L0/L1/L2 heading tree | `ontology_authoring.path`               | Domain, layer, and category allocation                              |
| Property drawer       | `ontology_authoring.properties`         | Stable ids, API names, primary keys, status, owners, and provenance |
| TODO state            | `ontology_authoring.lifecycle_state`    | Draft, candidate, review, accepted, or retired authoring state      |
| Tags                  | `ontology_authoring.tags`               | Domain, interface, risk, route, and validation hints                |
| Tables                | `ontology_authoring.tables`             | Object, link, action, query, interface, and value-type declarations |
| Source blocks         | `ontology_authoring.embedded_artifacts` | Optional RDF/TOML/SQL examples or generated previews                |
| Source range          | `ontology_authoring.source_span`        | Reopenable validation and review location                           |

The parser may compile accepted Org authoring documents into RDF/TOML/API
surface artifacts, but generated artifacts must stay reproducible and
validation-gated. Hand-authored RDF/TOML may remain supported for interop and
bootstrap, but Org is the stronger syntax for agent-facing ontology authoring.

## 6. JSON Schema Contract Layer

JSON Schema is the clean validation layer for parser-owned DTOs compiled from
Org authoring documents and Org traces. It should validate structural contract
facts such as required source identity, source spans, lifecycle state,
authoring kind, table shape, evidence presence, and candidate payload shape.

This layer does not replace Org-mode as the authoring syntax. Humans and
sub-agents should not be forced to hand-author JSON for ontology proposals.
They author Org; `xiuxian-wendao-parsers` compiles that Org into DTOs; JSON
Schema validates those DTOs before preview generation, candidate creation, or
future runtime import.

The first schema files should remain draft/internal until real parser fixtures
and source-contract previews stabilize:

1. `org_ontology_authoring_contract.schema.json`
2. `org_trace_projection_contract.schema.json`
3. `ontology_candidate_contract.schema.json`

These schemas are parser contracts, not public runtime wire schemas. They do
not encode full ontology semantics, RDF reasoning, SQL validation, or semantic
SSOT acceptance.

## 7. Org Trace Contract

An Org trace should be treated as a structured evidence document. The first
projection slice should support these trace units:

| Org unit          | Parser-owned projection     | Ontology use                                                       |
| ----------------- | --------------------------- | ------------------------------------------------------------------ |
| Heading path      | `trace_section.path`        | Candidate scope and provenance anchor                              |
| TODO state        | `trace_section.state`       | Workflow state evidence                                            |
| Property drawer   | `trace_section.properties`  | Candidate ids, confidence, source ids, and validation hints        |
| Tags              | `trace_section.tags`        | Route, domain, and risk hints                                      |
| Planning metadata | `trace_section.planning`    | Deadline or scheduled validation evidence                          |
| Table             | `trace_table.rows`          | Candidate relation rows, validation findings, or action parameters |
| Source range      | `trace_section.source_span` | Reopenable provenance and self-correction location                 |

These rows are projections. They may feed semantic candidate creation, but they
do not mutate `semantic/`, `wendao-episteme/ontology/`, or any generated
registry by themselves.

## 8. Candidate Projection Flow

The calibrated flow is:

1. A human or sub-agent authors an Org ontology document, or a sub-agent emits
   an Org trace for a reasoning step, extraction result, or proposed ontology
   edit.
2. `xiuxian-wendao-parsers` parses the Org input with `orgize` and normalizes
   it into typed ontology-authoring rows or typed trace rows.
3. JSON Schema validates the compiled DTO shape for required property keys,
   table shapes, heading structure, source identity, evidence presence, and
   source spans.
4. The parser compiles valid ontology-authoring rows into source-contract
   artifacts or candidate semantic evidence: object hints, relation hints,
   action evidence, query declarations, interface declarations, validation
   findings, or generated artifact previews.
5. The repo-native semantic SSOT validator checks candidate status, confidence
   source, active change-intent binding, relation endpoints, lifecycle edges,
   and projection freshness.
6. Accepted Org/RDF artifacts are compiled into Arrow/Parquet read-model rows
   for runtime search, proof, SQL validation, Julia graph scoring, and Flight
   transport.
7. Only accepted candidates become canonical semantic objects or relations.

Invalid Org syntax, malformed property drawers, missing candidate ids, invalid
table shapes, unknown relation kinds, missing evidence anchors, or unbound
candidate suggestions must fail as validation evidence. Correctness wins over
agent convenience.

## 9. Relationship to Foundry-Style Ontology APIs

Palantir Foundry-style ontology systems expose objects, links, actions,
queries, transactions, and interfaces as the operating API. Wendao should
adopt that shape at the parser-contract level before exposing runtime routes:

1. Org traces may propose action parameters or transaction edits.
2. Parser-owned ontology contracts should normalize object, link, action,
   query, interface, and value-type metadata.
3. Runtime surfaces should serve validated metadata and bounded evidence, not
   raw LLM traces.
4. Mutations should be expressed as action proposals or transaction edits that
   pass validation before writeback.

This keeps the agent-facing API aligned with ontology concepts while preserving
repo-native authority.

## 10. Non-Goals

This slice does not:

1. make raw Org-mode output canonical without parser compilation and semantic
   acceptance
2. make `orgize` a database or ontology authority
3. claim zero-copy DuckDB or Arrow projection as implemented
4. bypass semantic SSOT lifecycle validation
5. let LLM output promote candidates directly
6. replace RDF/TOML source contracts in `wendao-episteme`
7. add a new runtime route or public wire schema
8. make JSON Schema the primary authoring syntax
9. preserve TSV as a canonical ontology or search data surface

## 11. First Implementation Slice

The first physical slice should stay in `xiuxian-wendao-parsers`:

1. define draft JSON Schema contracts for parser-owned Org ontology authoring,
   Org trace projection, and ontology candidate DTOs
2. define parser-owned Org ontology authoring DTOs and Org trace DTOs
3. parse heading paths, TODO state, property drawers, tags, planning metadata,
   tables, source blocks, and source spans with `orgize`
4. validate a small required property vocabulary for ontology authoring and
   ontology-candidate traces
5. convert valid authoring documents and traces into source-contract previews
   or candidate evidence rows
6. reject malformed traces with precise source locations
7. add focused parser tests using native Org property drawers, tables, and
   schema-validated DTO fixtures

The first implementation may land in two bounded steps: first heading path,
property drawer, TODO/status, tags, and source spans; then table and source
block projection. Both steps must validate real parser output against the
draft JSON Schema contracts.

Runtime integration into Wendao, SQL validation, Qianji workflow routing, and
Julia graph scoring should follow only after the parser contract is stable.

## 12. Open Questions

1. Which property keys should be required for candidate object proposals?
2. Should relation proposal tables use one table per relation kind or one
   normalized relation table shape?
3. Should action proposals reuse the ontology `api_surface.toml` action names
   directly, or should they first pass through an action-alias resolver?
4. Which trace fields should be included in the first `OntologyFullMetadata`
   parser contract?
5. How much of the Org trace should be preserved after candidate acceptance:
   full trace, compact provenance row, or source-span pointer only?

## 13. Verdict

Org-mode is approved as the primary authoring syntax for agent-facing ontology
proposals and as the reasoning/evidence carrier for agent traces. `orgize` is
approved as the native parser for turning that syntax into typed authoring and
projection rows. JSON Schema is approved as the draft validation layer for
compiled parser DTOs. Ontology truth remains source-contract-first under
`wendao-episteme` and validation-first under Rust-owned parser and semantic
SSOT contracts.
